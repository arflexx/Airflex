# Deployment & Production Runbook

This guide covers deploying the AirFlex API server, Soroban smart contracts, and documentation site to production, alongside operational runbooks for secret rotation, zero-downtime deployments, rollbacks, and incident response.

---

## 1. Production Environment Variables Reference

The server verifies configuration at startup via `envSchema`. Missing required variables will cause process exit with error telemetry. All variables are tracked in [`server/.env.example`](https://github.com/arflexx/Airflex/blob/main/server/.env.example).

### Required Minimum Variables
| Variable | Category | Description |
|---|---|---|
| `DATABASE_URL` | Database | PostgreSQL connection string (`postgresql://user:pass@host:5432/db`). |
| `JWT_SECRET` | Security | Minimum 32-character high-entropy secret for signing authentication tokens. |
| `ESCROW_CONTRACT_ADDRESS` | Soroban | Deployed Soroban escrow contract address (starts with `C`). |

## 2. Zero-Downtime Deployment Strategy on Railway

AirFlex uses Railway Nixpacks builds configured in `railway.json`.

```json
{
  "build": {
    "builder": "NIXPACKS",
    "buildCommand": "pnpm install --frozen-lockfile && pnpm build",
    "watchPatterns": ["server/src/**"]
  },
  "deploy": {
    "startCommand": "pnpm start",
    "healthcheckPath": "/health",
    "healthcheckTimeout": 100,
    "restartPolicyType": "ON_FAILURE",
    "restartPolicyMaxRetries": 3
  }
}
```

### Rolling Deployment Workflow
1. **Healthcheck Probe**: Railway starts the new deployment container and monitors `GET /health` (`healthcheckPath`).
2. **Traffic Switch**: The existing running container continues serving ingress traffic until the new container returns `HTTP 200 {"status":"ok"}`.
3. **Graceful Shutdown**: Once the new container is healthy, incoming requests are routed to the new instance, and the old container receives `SIGTERM`. The server closes idle connections and completes active requests within a 15-second grace window before exiting.

## 3. Secret Rotation Procedures (Without Downtime)

### A. JWT Secret (`JWT_SECRET`)
To rotate the authentication signing key without abruptly terminating all user sessions:
1. **Dual-Key Support**: Configure the server to accept a comma-separated list `JWT_SECRET=new_secret_key,old_secret_key`.
2. **Signing vs. Verification**: The server signs all newly issued tokens using `new_secret_key` while verifying incoming tokens with either key.
3. **Session Rollover**: Wait for the session duration (e.g., 7 days) until active tokens have transitioned.
4. **Decommission**: Remove `old_secret_key` from the environment variable.

### B. Database Credentials (`DATABASE_URL`)
1. Create a secondary database user with identical role permissions in PostgreSQL:
   ```sql
   CREATE USER airflex_worker_v2 WITH PASSWORD 'new_secure_password';
   GRANT airflex_app_role TO airflex_worker_v2;
   ```
2. Update `DATABASE_URL` in Railway dashboard.
3. Railway triggers a rolling deployment. The new container connects using `airflex_worker_v2`, while old containers drain their pool connections.
4. After verifying the release is active and old containers have shut down, revoke and drop the old database user.

### C. Oracle Signer Secret (`ADMIN_SECRET_KEY`)
1. Generate a new Stellar keypair for the admin oracle.
2. In the Soroban Escrow contract, call `transfer_admin(new_address)` from the current admin account.
3. Update `ADMIN_SECRET_KEY` in Railway environment settings to the new private key.
4. Verify `/health` and test oracle transaction signing on testnet/mainnet.

## 4. Rollback Runbook (Rapid Incident Recovery)

If a newly deployed release introduces critical regression, perform a rollback immediately:

### Option 1: Railway Web Console (1-Click Rollback)
1. Navigate to **Railway Dashboard → Project → Service (server)**.
2. Click on the **Deployments** tab.
3. Locate the last known good deployment (prior green commit).
4. Click the three dots `...` next to that deployment and select **Rollback to this deployment**.
5. Railway routes traffic back to the previous deployment artifact in under 30 seconds without rebuilding.

### Option 2: Railway CLI Rollback
```bash
# Authenticate Railway CLI
railway login

# Select environment
railway environment production

# Redeploy previous deployment ID
railway rollback
```

### Option 3: Git Revert (Permanent Fix)
```bash
git checkout main
git pull origin main
git revert HEAD -m "revert: rollback release due to incident"
git push origin main
```

## 5. Production Incident Response Runbook

### Incident 1: Database Connection Failure / Pool Exhaustion
* **Symptoms**: Logs show `error: connection timeout`, `remaining connection slots are reserved for non-replication superuser connections`, or `ETIMEDOUT`.
* **Immediate Mitigation**:
  1. Check connection counts in PostgreSQL:
     ```sql
     SELECT count(*), state FROM pg_stat_activity GROUP BY state;
     ```
  2. Terminate idle in transaction connections:
     ```sql
     SELECT pg_terminate_backend(pid) FROM pg_stat_activity WHERE state = 'idle in transaction' AND state_change < current_timestamp - INTERVAL '5' MINUTE;
     ```
  3. Reduce `DATABASE_MAX_POOL` in environment if multiple server replicas exceed PostgreSQL `max_connections`.
  4. Ensure connection pooling (e.g. PgBouncer) is active between Railway containers and database.

### Incident 2: Redis Eviction / Queue Stalling
* **Symptoms**: Trades remain in `Locked` status without oracle processing; BullMQ logs report `OOM command not allowed` or `Job stalled`.
* **Immediate Mitigation**:
  1. Inspect Redis memory usage: `redis-cli INFO memory`.
  2. If memory limit reached, configure `maxmemory-policy volatile-lru` or upscale the Redis instance.
  3. Restart the background worker queue process:
     ```bash
     railway restart --service worker
     ```
  4. Re-enqueue stalled jobs via BullMQ dashboard / maintenance script.

### Incident 3: Stellar / Soroban RPC Outage
* **Symptoms**: API returns `504 Gateway Timeout` or `Failed to simulate transaction` during escrow operations.
* **Immediate Mitigation**:
  1. Verify network status on Stellar Status page (`https://status.stellar.org`).
  2. Switch `SOROBAN_RPC_URL` and `HORIZON_URL` to fallback backup providers (e.g., ValidationCloud, NowNodes, or Blockdaemon).
  3. Trigger zero-downtime rolling config update in Railway.
